# Вкладка «Логи»: пользовательская логика и архитектура

Документ описывает журнал действий внутри мероприятия: что видит пользователь, какие действия попадают в лог и как это реализовано на frontend/backend.

---

# Часть 1. Для пользователя системы

## 1. Назначение вкладки

Вкладка **«Логи»** показывает историю действий, которые меняли состояние мероприятия или связанных с ним данных.

Журнал нужен, чтобы быстро понять:

- кто выполнил действие;
- когда это произошло;
- какая сущность была изменена;
- что именно было сделано по смыслу.

Например, если создан гость, в логе отображается действие создания, пользователь-исполнитель и описание с ФИО гостя. Если применена оригинальная оргструктура, в описании видно количество созданных и переиспользованных групп.

## 2. Доступ

Вкладка доступна авторизованному пользователю внутри выбранного мероприятия.

Backend дополнительно проверяет, что пользователь имеет профиль в этом мероприятии. Если пользователь не относится к мероприятию, запрос логов будет отклонён.

## 3. Как отображаются логи

Логи отображаются в компактной таблице.

Колонки:

| Колонка | Что показывает |
|---|---|
| **Когда** | дата и время действия |
| **Кто** | имя пользователя и его роль, если она известна |
| **Действие** | человекочитаемый тип действия, если для кода есть frontend-подпись; иначе отображается технический код |
| **Сущность** | тип объекта: мероприятие, гость, группа, категория, метка, сотрудник |
| **Информация** | заголовок лога и дополнительное описание |

Каждая запись занимает одну строку. Отдельная «лента» с вертикальной шкалой времени не используется, чтобы журнал занимал меньше места и быстрее читался глазами.

## 4. Поиск

Над таблицей есть поле **«Поиск по описанию»**.

Поиск применяется с небольшой задержкой после ввода. Чтобы не создавать слишком много запросов, строка начинает участвовать в фильтрации только если введено минимум два символа.

Поиск предназначен для прикладных деталей: имени гостя, названия группы, категории, метки, файла структуры и других значимых фрагментов из `title`/`description`.

## 5. Фильтры

Кнопка **«Фильтровать»** открывает модальное окно фильтров.

Доступные фильтры:

- пользователь;
- действие;
- сущность;
- дата с;
- дата по.

Поля дат расположены в одну строку. После настройки нужно нажать **«Применить»**. Кнопка **«Сбросить»** очищает все фильтры и поиск.

На кнопке фильтрации показывается количество активных фильтров.

## 6. Пагинация

Логи загружаются постранично.

Пользователь может:

- перейти на предыдущую или следующую страницу;
- выбрать размер страницы: `10`, `20` или `50`;
- видеть диапазон отображаемых записей и общее количество найденных логов.

## 7. Какие действия логируются

В журнал попадают основные операции, которые меняют данные мероприятия:

- создание, редактирование и удаление гостей;
- изменение статусов гостей;
- создание, редактирование и удаление категорий;
- создание, редактирование и удаление меток;
- создание, редактирование, удаление и сброс групп;
- загрузка и применение оригинальной организационной структуры;
- создание и изменение сотрудников;
- сброс пароля сотрудника;
- изменение состояния мероприятия;
- загрузка обложки/изображения мероприятия.

Лог создаётся сервером после успешного выполнения операции. Если операция не прошла валидацию или была отклонена по правам, запись в журнал не добавляется.

# Часть 2. Для разработчика

## 1. Модель данных

Основная сущность:

```text
EventLog
  ├── Id
  ├── EventId
  ├── UserId?
  ├── ActorName
  ├── ActorRoleName?
  ├── Action
  ├── EntityType
  ├── EntityId?
  ├── Title
  ├── Description?
  └── CreatedAt
```

Таблица БД: `event_logs`.

Назначение полей:

| Поле | Назначение |
|---|---|
| `event_id` | мероприятие, внутри которого произошло действие |
| `user_id` | сотрудник мероприятия, который выполнил действие; nullable |
| `actor_name` | сохранённое имя исполнителя на момент действия |
| `actor_role_name` | сохранённая роль исполнителя на момент действия |
| `action` | технический код действия |
| `entity_type` | тип сущности |
| `entity_id` | ID изменённой сущности, если применимо |
| `title` | короткий заголовок для таблицы |
| `description` | прикладные детали действия |
| `created_at` | дата и время создания записи |

`UserId` nullable специально: если сотрудник позже будет удалён, история не должна пропадать. При удалении пользователя связь выставляется в `NULL`, а `ActorName` и `ActorRoleName` остаются в записи.

## 2. Индексы и связи

Конфигурация находится в:

- `corebackend/src/Infrastructure/Data/Configurations/EventLogConfiguration.cs`.

Основные индексы:

- `(event_id, created_at)`;
- `(event_id, user_id, created_at)`;
- `(event_id, action, created_at)`;
- `(event_id, entity_type, created_at)`.

Связи:

- `Event -> EventLogs`: `Cascade`;
- `User -> EventLogs`: `SetNull`.

## 4. API

Базовый маршрут:

```text
/api/events/{eventId}/logs
```

Контроллер защищён `[Authorize]`.

### Получение страницы логов

```http
GET /api/events/{eventId}/logs
```

Query-параметры:

| Параметр | Тип | Назначение |
|---|---|---|
| `page` | `int` | номер страницы, по умолчанию `1` |
| `pageSize` | `int` | размер страницы, по умолчанию `20` |
| `userId` | `long?` | фильтр по исполнителю |
| `action` | `string?` | фильтр по коду действия |
| `entityType` | `string?` | фильтр по типу сущности |
| `search` | `string?` | поиск по `title` и `description` |
| `dateFrom` | `DateTimeOffset?` | нижняя граница даты |
| `dateTo` | `DateTimeOffset?` | верхняя граница даты |

Ответ:

```text
PagedResultDto<EventLogDto>
```

### Получение опций фильтров

```http
GET /api/events/{eventId}/logs/filter-options
```

Возвращает:

- список пользователей, встречающихся в логах;
- список кодов действий;
- список типов сущностей.

## 6. Frontend-состояние вкладки

`EventLogsPage` хранит:

- текущую страницу и размер страницы;
- общее количество записей;
- загруженный список логов;
- опции фильтров;
- применённые фильтры;
- черновики фильтров внутри модального окна;
- строку поиска и debounced-значение поиска.

Поиск по описанию debounce’ится на `450 ms`. Если после `trim()` введено меньше двух символов, параметр `search` не отправляется.

## 7. Коды действий и сущностей

На frontend коды преобразуются в человекочитаемые подписи через словари `actionLabels` и `entityLabels`. Если код отсутствует в словаре, пользователь увидит исходное техническое значение.

Текущие известные действия:

- `created`;
- `updated`;
- `deleted`;
- `submitted_for_review`;
- `reviewer_approved`;
- `admin_approved`;
- `rejected`;
- `invited`;
- `restored_to_saved`;
- `archived`;
- `restored`;
- `password_reset`;
- `cover_uploaded`;
- `original_structure_imported`;
- `original_structure_applied`;
- `groups_reset`.

Текущие известные сущности:

- `Event`;
- `Guest`;
- `Category`;
- `Tag`;
- `Group`;
- `User`;
- `OrganizationStructure`.

Если добавляется новый код действия или новая сущность, нужно:

1. начать писать лог на backend через `IEventLogService`;
2. добавить человекочитаемую подпись в `EventLogsPage.tsx`, если не хочется показывать технический код пользователю.

## 8. Как добавлять логирование в новый сценарий

В сервисе, который успешно изменил состояние БД, нужно вызвать:

```csharp
await eventLogService.AddAsync(
    eventId,
    loginId,
    action,
    entityType,
    entityId,
    title,
    description);
```

Рекомендации:

- `action` держать коротким стабильным кодом;
- `entityType` писать в едином стиле с уже существующими значениями;
- в `title` помещать краткое действие;
- в `description` помещать прикладную информацию: ФИО гостя, название категории, количество созданных групп и т.д.;
- писать лог после успешного сохранения основных изменений;
- если операция выполняется в транзакции, лог должен попадать в ту же транзакцию.
