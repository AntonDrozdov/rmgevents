# AIMode

Кнопка под логотипом открывает модальный чат на дашборде и страницах мероприятия, включая мобильный интерфейс. Enter отправляет вопрос, Shift+Enter переносит строку. Новый чат очищает историю; закрытие окна сохраняет диалог до ухода со страницы. История хранится только в памяти компонента.

## Настройка Yandex AI Studio

Официальная документация: https://aistudio.yandex.ru/ru/docs/ai-studio/operations/generation/completions-basic и https://aistudio.yandex.ru/ru/docs/ai-studio/operations/models/get

1. Создайте API-ключ в AI Studio. Для сервисного аккаунта требуется роль `ai.languageModels.user`, области ключа — `yc.ai.foundationModels.execute` и `yc.ai.models.viewer`. У облака должен быть активный платёжный аккаунт.
2. Из корня репозитория выполните `powershell -NoProfile -ExecutionPolicy Bypass -File .\deploy\setup-ai.ps1`. Скрипт запросит ID каталога и ключ со скрытым вводом, затем сохранит их в `deploy/.env.ai`, игнорируемый Git. Не записывайте ключ в `deploy/.env`: этот файл отслеживается Git и содержит только APP_VERSION. Модель в `.env.ai` больше не задаётся. Docker Compose должен быть версии 2.24 или новее.
3. Пересоберите приложение и пересоздайте контейнеры по инструкции deploy/README.md. Для запуска без Docker передайте серверу только `YandexAI__ApiKey` и `YandexAI__FolderId`.

Сервер вызывает `POST https://ai.api.cloud.yandex.net/v1/chat/completions` с `Authorization: Api-Key …`, `OpenAI-Project` и URI выбранной пользователем модели `gpt://<каталог>/<модель>`. Ключ и SID пользователя не передаются в содержимое запроса к модели; SID проверяется существующей авторизацией приложения.

## Выбор модели

При каждом открытии AIMode frontend вызывает авторизованный `GET /api/assistant/models`, а backend запрашивает `GET https://ai.api.cloud.yandex.net/v1/models` с заголовками `Authorization: Api-Key …` и `x-project`. Полученный список используется в выпадающем поле выбора модели. Информационное окно со всем списком показывается только при первом открытии AIMode в текущей вкладке браузера; признак хранится в `sessionStorage`.

Файл `deploy/yandexmodels_29102026.md` служит только локальным справочником цены, названия, контекста и ценового ранга для известных идентификаторов. Известные модели располагаются от более дешёвых к более дорогим, а новые модели, которые вернул Yandex, также доступны в интерфейсе и идут после них с пометкой об отсутствии локальной цены. Выбор хранится в `localStorage` браузера и применяется к следующему отправленному сообщению, включая все обращения к модели и вызовы инструментов внутри этого сообщения. Смена модели сама по себе не очищает уже отображаемую историю; для полностью независимого контекста используйте кнопку «Новый чат».

Frontend передаёт короткий ID модели в `POST /api/assistant/ask`. Backend разрешает его только через последний полученный список Yandex и передаёт в Chat Completions точный URI, который вернул Models API; произвольный URI от frontend не принимается. Список кэшируется backend на 10 минут для проверки последующих запросов, но при каждом открытии модального окна принудительно обновляется. Переменная `YandexAI__Model` больше не читается.

## Доступ и границы

`POST /api/assistant/ask` требует авторизации. Сервер повторно проверяет участие пользователя в выбранном мероприятии и сам получает роль и permissions. Клиент передаёт путь страницы, ID мероприятия, выбранный ID модели и диалог. В Яндекс отправляются сообщения и ограниченный контекст: название, дата, архивный статус мероприятия, роль, ID группы и права; на дашборде — первые 50 доступных мероприятий. Персональные карточки гостей и сотрудников автоматически не отправляются.

Ассистент консультирует по разделам приложения и может подготовить изменение настроек текущего мероприятия с подтверждением пользователем. Он не имеет инструментов выполнения команд и доступа к произвольным API. Справка включена в сборку из `AssistantKnowledge.cs` и подготовлена по документации и сервисным правилам репозитория. Ограничение тематики задаётся системной инструкцией модели; абсолютная гарантия тематического отказа для любого запроса невозможна. Права доступа обеспечиваются сервером независимо от ответов модели.

Лимит: 10 запросов в минуту на пользователя в одном экземпляре сервера; до 19 сообщений и 40 000 символов истории, до 6000 символов вопроса и 12000 символов ответа в истории. Клиент автоматически удаляет старые пары сообщений из отправляемого контекста, сохраняя их на экране. Тайм-аут всей цепочки модели — 50 секунд, максимум 6 обращений к модели и 12 вызовов инструментов за вопрос, до 1600 токенов ответа за обращение. Дополнительные шаги нужны, чтобы после нескольких зависимых чтений данных модель успела создать карточку изменения, а не завершила ответ текстовой просьбой о подтверждении. Ответ провайдера ограничен 256 КБ. Тела запросов и ответов модели не логируются. Без ключа или каталога сервер возвращает понятное сообщение о необходимости настройки.

Под каждым ответом AIMode показывается фактическое использование токенов, возвращённое Yandex AI Studio: входные, выходные и общие токены. Если для одного сообщения потребовалось несколько обращений к модели из-за инструментов чтения или подготовки действия, значения суммируются по всей цепочке.

## Инструменты чтения

Инструменты реализованы через function calling Chat Completions API: https://aistudio.yandex.ru/en/docs/ai-studio/operations/generation/completions-function

- `get_event_summary`: число активных гостей по статусам в своей ветке групп.
- `list_guests`: до 100 гостей по именам, отсортированных по имени, с общим количеством и признаком усечения; контакты не возвращаются.
- `search_guests`: поиск по части имени, минимум 2 символа; до 20 результатов, без email, телефона и публичных ссылок. Возвращает имя, статус, группу и назначенное место.
- `get_guest_neighbors`: поиск одного гостя и определение занятых и свободных соседних мест; для стола учитывается соседство первого и последнего места.
- `get_groups`: до 100 групп своей ветки, квоты и сумма квот непосредственных детей. Требуется `create_group`.
- `get_placements`: до 100 объектов с группой в своей ветке, вместимость, занятые и свободные номера мест по каждому объекту и итоговые `totalSeats`, `occupiedSeats`, `availableSeats`; требуется `create_group` или `create_guest`. Объекты других веток и декоративные подписи исключаются.
- `get_event_catalogs`: ID категорий и меток, а при наличии соответствующих permissions — ролей, сотрудников и шаблонов. Контакты сотрудников не передаются.

Каждый инструмент заново проверяет членство в мероприятии, права и область групп. Параметры loginId, eventId и groupId модель передать не может. Запросы EF используют только чтение, параметризованные условия и фильтры мероприятия. Поиск и сводка исключают удалённых гостей. В интерфейсе отображаются названия успешно использованных источников. Имена гостей и названия объектов передаются Яндексу только при запросе соответствующего инструмента; об этом сообщается в окне чата.

`get_placements` возвращает для каждого доступного объекта массивы `occupiedSeatNumbers` и `availableSeatNumbers` с учётом начального номера. Для команды вида «пересади Иванова на другое место за тем же столом» модель находит гостя через `search_guests`, сохраняет его текущий `placementId`, выбирает другой свободный номер и готовит `reseat_guest`. Каталог преобразует операцию в обычное обновление гостя и сам дополняет имя, контакты, группу, категорию и метки актуальными значениями. Поэтому пересадка не стирает остальные данные гостя и не использует неоднозначное назначение объекту без точного места.

Для явных фактических вопросов backend определяет требуемый read-инструмент до обращения к модели и передаёт Yandex именованный `tool_choice` вместе с защищёнными сервером аргументами. «Сколько гостей» вызывает сводку, «выведи гостей по именам» — список, «есть ли гость Ельцин» — `search_guests` с запросом `Ельцин`, а «с кем рядом сидит Петров» — `get_guest_neighbors` с запросом `Петров`. Это не позволяет модели заменить запрос советом вызвать внутреннюю функцию или потерять имя. Короткий вопрос вида «сколько их?» может унаследовать тему из последних пользовательских сообщений. Для команды «посади А рядом с Б» сначала принудительно определяется рассадка Б, после чего модель находит А и готовит точную пересадку.

Совместимые модели иногда возвращают для функции без параметров оболочку `{"properties":{}}` либо печатают имя функции обычным текстом. Для read-инструментов без аргументов backend нормализует такую оболочку в `{}`. Если модель упомянула внутреннее имя вместо структурированного вызова, сервер сам выполняет безопасный read-инструмент и повторяет генерацию; техническое имя инструмента не должно попадать в ответ пользователю.

## Изменения через агента

Предложенное изменение сначала остаётся карточкой в чате. Кнопка `Проверить и выполнить` открывает отдельный диалог поверх AIMode. Для создания и изменения гостя карточка показывает одну компактную фразу с именем и только существенными данными; сервер заменяет ID категории, группы, меток и размещения понятными названиями, когда они доступны. Остальные операции показывают список значений «Сейчас» и «После выполнения». Пользователь может выполнить действие или отказаться, не переходя на экраны приложения. После подтверждения запрос выполняется в фоне через обычный API с текущей сессией и повторной проверкой прав, диалог закрывается, а итог отображается в том же чате. Обновление страницы для завершения операции не требуется.

`propose_action` поддерживает закрытый серверный список операций: мероприятия; создание, редактирование, статусы, удаление, восстановление и массовые действия гостей; группы и шаблоны групп; категории и метки; сотрудники; схема и назначение мест; шаблоны размещения и билетов. Доступность определяется текущими permissions (`create_event`, `create_guest`, `approve_guest`, `create_group`, `create_user`) и областью групп пользователя.

Если одна команда требует от 2 до 25 независимых изменений, модель использует `propose_actions`. Backend проверяет каждую вложенную операцию тем же каталогом и формирует одну карточку с общим списком. Пользователь подтверждает пакет одной кнопкой, после чего frontend последовательно вызывает обычный API для каждого элемента. Для каждого запроса используется отдельный стабильный ключ повторного выполнения, поэтому несколько запросов на один endpoint не смешиваются. Результат показывает число успешно выполненных элементов и номера ошибок. Поскольку операции проходят через отдельные HTTP-запросы, пакет не является общей транзакцией: при ошибке возможен частичный результат, который явно показывается в чате.

Для структурных изменений схемы размещения каталог операции выставляет защищённый признак необходимости edit-lock. Перед подтверждением AIMode автоматически продлевает уже принадлежащую пользователю блокировку либо пытается получить новую. Если схема занята другим сотрудником, пакет не запускается и чат показывает владельца блокировки; чужая блокировка автоматически не перехватывается. Полученная специально для AIMode блокировка освобождается после выполнения пакета. Сообщения ошибок обычного API выводятся вместе с номером неуспешного элемента, а не заменяются одним кодом HTTP.

Модель не может передать HTTP-метод или URL: они выбираются `AssistantActionCatalog` из жёсткого списка. Сервер проверяет операцию, членство и permission, сохраняет предложение на 10 минут и возвращает карточку. Подтверждение выполняется отдельным `POST /api/assistant/actions/{id}/decision` с `{eventId, confirm}`. Идентификатор карточки не передаётся модели. После подтверждения запрос выполняется frontend через обычный API с текущим SID, поэтому контроллеры и сервисы повторно проверяют роль, ветку групп, архивность, валидацию и блокировку редактирования размещения.

Для update-операций модель может передать только изменяемые поля. Сервер читает актуальную запись и дополняет обязательные поля перед созданием карточки, поэтому изменение группы гостя не стирает его контакты, категорию, метки или место. Карточка показывает только понятное описание действия и значимые значения «Сейчас»/«После выполнения». HTTP-метод, URL и служебное тело запроса пользователю не показываются, хотя остаются зафиксированы в закрытом серверном каталоге операции.

Для create-операций сервер также нормализует минимальный набор данных. AIMode спрашивает только отсутствующие обязательные поля и не требует необязательные контакты, описания, цвета или координаты. Для гостя группа по умолчанию равна группе сотрудника, метки пусты, а единственная категория мероприятия выбирается автоматически; при нескольких категориях категория уточняется. Для новой группы достаточно названия: квота по умолчанию равна `0`, родителем становится группа сотрудника. Категория получает цвет `#292962`, метка — `#FFFFFF`. Для сотрудника обязательны логин, имя, фамилия и роль, а группа по умолчанию текущая. Новый объект размещения без дополнительных указаний создаётся как стол на 10 мест в текущей группе. Для шаблона билета обязательны название и ранее загруженная подложка, а координаты QR берутся из стандартной формы приложения. Явно указанные пользователем значения всегда имеют приоритет над значениями по умолчанию.

Специализированные операции изменения мероприятия дополнительно блокируют строку мероприятия и сравнивают снимок данных, чтобы не перезаписать параллельное редактирование. Все остальные операции используют неизменённые прикладные API. Результат массовой операции и временный пароль сотрудника показываются в карточке после выполнения.

Не поддерживаются изменение состава permissions роли (такого API в приложении нет), физическое удаление мероприятия, загрузка изображений и импорт XLSX: чат не получает содержимое файла. Kafka для синхронного выполнения команд не используется.

Подтверждения хранятся в памяти backend с TTL 10 минут. Подтверждённый запрос получает `X-Assistant-Action-Id`, а ответ обычного API кешируется в памяти на 15 минут: последовательный повтор после потери сетевого ответа не создаёт объект второй раз. При перезапуске backend этот временный кеш очищается; решение рассчитано на один экземпляр backend.

## Платформа

Backend переведён на .NET 10 / ASP.NET Core 10, EF Core 10.0.14 и Npgsql EF 10.0.3. Frontend собирается Node 24 и работает в Nginx 1.30.6. В текущей конфигурации Redis и Kafka не используются.

## Автоматические проверки

`dotnet run --project corebackend/tests/AssistantChecks/AssistantChecks.csproj` проверяет историю, ограничения групп, запрет произвольных инструментов, маршрутизацию сводки/списка гостей, компактные карточки, нормализацию пустых аргументов совместимых моделей, защиту от текстовых имён функций, протокол вызовов, отмену, ограничения ответа модели и HTTP-контракт контроллера (401, 400, 403, 503, 429). Используются тестовый HTTP-провайдер и отдельный HTTP-хост без рабочей базы и реальной модели. Эти проверки не заменяют живой проверки выбранной модели и запросов к PostgreSQL.

При заданной переменной `ASSISTANT_TEST_POSTGRES` дополнительно создаётся отдельная база с уникальным именем `assistant_checks_<guid>`, применяются миграции и проверяются реальные PostgreSQL-запросы: изоляция групп и мероприятий, исключение удалённых гостей и контактов, сортировка и усечение списка после 100 записей, счётчик мест, поиск и буквальная обработка SQL-подобного текста. В конце временная база удаляется. Строка подключения должна разрешать создание баз; рабочая база из строки подключения не изменяется.

## Перенос на сервер

Файл `.env.ai` не включается в Git, Docker-образы и текущий скрипт переноса образов. Создайте его отдельно в каталоге серверного compose с переменными `YandexAI__ApiKey` и `YandexAI__FolderId`, ограничьте доступ к файлу средствами ОС и пересоздайте backend. Модель выбирается в интерфейсе для каждого следующего запроса. Для первой проверки используйте локальный запуск, затем выбранное тестовое мероприятие. Лимит запросов сейчас действует отдельно на каждый экземпляр backend; расходы отслеживаются в консоли Яндекса.

## Проверка после настройки

Войдите в приложение, откройте AIMode и спросите: «сколько гостей в мероприятии» и «сколько доступных мест в рассадке». В обоих ответах должен появиться источник данных, а не предложение вручную вызвать внутреннюю функцию. Затем проверьте создание гостя с карточкой подтверждения, ответ на посторонний вопрос, новый чат, отмену и мобильный интерфейс. Через API проверьте 401 без SID, 403 при ID чужого мероприятия и 429 после превышения лимита. Реальный ответ модели требует действующего ключа и каталога.
