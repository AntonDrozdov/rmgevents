# Система управления мероприятиями — Техническое задание и план

## Краткая переформулировка задания
Разработать систему управления мероприятиями с ролевой моделью доступа. Пользователи логинятся и получают дашборд со списком мероприятий, в которых у них назначены роли. Роли — наборы разрешений, роли создаются внутри мероприятия. Внутри мероприятия реализуется иерархия групп (дерево) с корневой группой по умолчанию; у каждой группы — квота. Пользователи могут создавать гостей, сотрудников и дочерние группы в рамках прав и иерархии.

## Основные требования и логика работы
- Авторизация/логин:
  - Есть таблица логинов (`Logins`) с хешами паролей.
  - При логине выбираем все записи из таблицы `Users` с данным логином — пользователь может иметь записи для нескольких мероприятий.
  - После логина показываем дашборд с мероприятиями, в которых пользователь имеет роль.
- Сущность: **Мероприятие** — это основной контекст. Как только пользователь выбирает мероприятие, интерфейс и API работают в контексте этого мероприятия.
- Никогда не бывает ситуации, когда у пользователя нет никакой роли: у пользователя будет как минимум одна запись (роль) в каком-то мероприятии.
- Роли создаются внутри мероприятия и привязаны к набору разрешений.
- Группы:
  - Для каждого мероприятия при создании заводится корневая группа.
  - Группы образуют древовидную иерархию; пользователи с соответствующим правом могут создавать дочерние группы.
  - У каждой группы есть квота (число) — ограничение по гостям/местам.
- Гости: создаются внутри мероприятия и привязываются к группе.
  - Пользователь может создавать гостей в своей группе и в любой дочерней группе (ниже по иерархии).
- Разрешения, которые зависят от группы, при назначении роли должны сопровождаться указанием группы для пользователя.

## Перечень разрешений
- `create_event` — создание мероприятия
- `create_guest` — создание гостя (требуется указать группу)
- `create_group` — создание группы (требуется указать группу как родитель)
- `approve_guest` — согласование/подтверждение гостя (требуется указать группу)
- `create_user` — создание сотрудника (требуется указать группу)

## Роли (рекомендуемый набор)
- Примечание: каждый пользователь имеет только одну роль в рамках одного мероприятия. Если требуются дополнительные права, следует создать для пользователя новую роль или изменить существующую роль в мероприятии.
- Предопределённые роли:
  - Администратор — все разрешения
  - Менеджер — `create_guest`, `create_group` (и чтение/редактирование в рамках группы)
  - Согласующий (Approver) — `approve_guest` (с правами, привязанными к указанной группе)

## Предлагаемая модель хранения (таблицы)
- `Logins`:
  - `id`, `login`, `password_hash`, `created_at`
- `Events`:
  - `id`, `name`, `description`, `owner_id`, `created_at`
- `Roles`:
  - `id`, `event_id`, `name` (напр. Administrator, Manager), `created_at`
- `Permissions`:
  - `id`, `code` (напр. `create_guest`), `description`
- `RolePermissions` (связующая):
  - `role_id`, `permission_id`
- `Groups`:
  - `id`, `event_id`, `parent_group_id`, `name`, `quota`, `created_at`
- `Users` (контексты ролей в мероприятиях):
  - `id`, `login_id` (FK -> `Logins`), `event_id` (FK -> `Events`), `role_id` (FK -> `Roles`), `group_id` (FK -> `Groups`), `display_name`, `meta`
  - Примечание: одна учётная запись в `Logins` может иметь несколько записей в `Users` для разных мероприятий/ролей.
- `Guests`:
  - `id`, `event_id`, `group_id`, `created_by_user_id`, `status` (`pending`, `approved`, `rejected`), `meta`

## Авторизация и выдача прав на фронтенд
- При логине сервис возвращает список мероприятий, где у логина есть запись в `Users`.
- При входе в конкретное мероприятие API возвращает профиль пользователя в контексте мероприятия: роль, `group_id` и список разрешений (выгружаемый массив строк).
- Фронтенд строит UI, показывая возможные действия на основе этого списка разрешений.

## Правила, связанные с группами и квотами
- При создании группы внутри мероприятия указывается квота (целое неотрицательное число).
- Иерархическая валидация квот:
  - Сумма квот непосредственных дочерних групп не должна превышать квоту родительской группы. Проверка выполняется при создании и обновлении дочерней группы.
  - При изменении квот необходимо рекурсивно валидировать ограничения вверх по дереву, чтобы не нарушить invariant: для любой группы sum(quota(children)) <= quota(parent).
- Доступная вместимость группы для размещения гостей вычисляется как:
  - available(group) = quota(group) - sum(quota(children_of_group)).
  - Для корневой группы доступная вместимость рассчитывается по той же формуле: quota_root - sum(quota(direct_children_of_root)).
  - При добавлении гостя в группу необходимо убедиться, что `available(group) > 0`. В зависимости от политики учёта можно также учитывать уже созданных и активных гостей при принятии решения.
- Пользователь может создавать гостей в своей группе и в любом дочернем (descendant) узле иерархии.
- При назначении роли, требующей указания группы, поле `group_id` обязательно.

## API (примерный набор эндпоинтов)
- `POST /api/auth/login` — тело: `{login, password}` — ответ: `{token, events: [{id,name,role_name}]}`
- `GET /api/events` — список доступных мероприятий (альтернатива: берётся из `/auth/login`)
- `GET /api/events/{eventId}/me` — профиль пользователя в контексте мероприятия + список разрешений
- `GET /api/events/{eventId}/groups` — дерево групп
- `POST /api/events/{eventId}/groups` — создание группы (проверка прав `create_group`)
- `GET /api/events/{eventId}/guests` — список гостей (фильтры по группе)
- `POST /api/events/{eventId}/guests` — создание гостя (проверка `create_guest` + квота)
- `POST /api/events/{eventId}/guests/{id}/approve` — согласование (проверка `approve_guest`)
- `POST /api/events` — создание мероприятия (проверка `create_event`)
- `POST /api/events/{eventId}/users` — создание сотрудника (проверка `create_user`)

Все эндпоинты должны проверять JWT/сессию и дополнительные права на уровне роли + группы.

## UI/фронтенд — поведение
- После логина показываем дашборд с картами/строкой мероприятий, где у пользователя есть роль.
- При выборе мероприятия загружаем `/events/{id}/me` и отображаем интерфейс в зависимости от разрешений (кнопки `Добавить гостя`, `Создать группу` и т.д.).
- Формы создания гостей/сотрудников требуют выбора группы (если роль предполагает привязку к группе).

## Граничные случаи и правила консистентности
- Нельзя удалить группу, если в ней (или в дочерних) есть гости или сотрудники, если только не выполнена операция миграции/удаления их в другую группу.
-- Нельзя назначить пользователю роль с правами, требующими группу, без указания `group_id`.
-- Каждый пользователь может иметь только одну роль в рамках одного мероприятия. Если нужно расширить набор прав — создаётся новая роль и назначается пользователю, либо модифицируется существующая роль.
- При удалении мероприятия удаляются связанные группы/роли/пользователи/гости (cascade) или помечаются как архивированные — на выбор по требованиям.

## Пошаговый план реализации (микрозадачи)
1. Спроектировать и создать миграции БД: `Logins`, `Events`, `Roles`, `Permissions`, `RolePermissions`, `Groups`, `Users`, `Guests`.
2. Реализовать аутентификацию (`/auth/login`) и выдачу токена.
3. Реализовать выборку доступных мероприятий при логине и дашборд на фронтенде.
4. Реализовать API получения профиля в контексте мероприятия и выдачу списка разрешений.
5. Реализовать CRUD для групп с поддержкой иерархии и квот.
6. Реализовать CRUD для гостей и логику согласования с проверкой квот.
7. Реализовать управление ролями и назначение разрешений (UI + API).
8. Написать интеграционные тесты для: авторизация → выбор мероприятия → операции, требующие прав.
9. Документировать поведение API и права (OpenAPI/Swagger).

## Риски и замечания
- Решение о том, считается ли квота иерархической (включает дочерние группы) влияет на логику подсчёта и запросы; определиться заранее.
- Нужно точно определить модель, будет ли один пользователь иметь множество ролей в рамках одного мероприятия (в текущей схеме — одна запись `Users` на сочетание login+event, но можно расширить до нескольких ролей).
