# Вкладка «Категории»: пользовательская логика и архитектура

Документ описывает функциональность категорий внутри мероприятия. Он состоит из двух частей:

1. правила и сценарии для пользователя системы;
2. техническое описание для разработчика.

Термины:

- **категория** — цветная классификация гостя внутри конкретного мероприятия;
- **категория гостя** — единственная выбранная категория, связанная с гостем через отдельную таблицу;
- **цвет категории** — hex-значение вида `#RRGGBB`, которое используется только для визуального отображения.

---

# Часть 1. Для пользователя системы

## 1. Когда доступна вкладка

Вкладка **«Категории»** находится внутри выбранного мероприятия:

```text
/events/{eventId}/categories
```

Она отображается пользователям с разрешением `create_event`. Это тот же permission, который используется для управления настройками мероприятия.

Для стандартных ролей:

| Роль | Доступ к вкладке |
|---|---|
| `Administrator` | Да |
| `Manager` | Нет по умолчанию |
| `Creator` | Нет по умолчанию |
| Пользовательская роль | Да, если роли назначено `create_event` |

Если мероприятие завершено, категории доступны только для просмотра. Создание, редактирование и удаление скрыты на frontend и запрещены на backend через `EventStateGuard`.

## 2. Список категорий

Вкладка показывает плоский список категорий текущего мероприятия.

В таблице отображаются:

- название;
- цвет;
- дата создания;
- действия редактирования и удаления.

Название категории отображается не как статусное облако, а как широкая двунаправленная стрелка с текстом внутри. Это сделано специально, чтобы визуально отделить категории от статусов гостей.

Редактирование можно открыть двумя способами:

1. нажать иконку карандаша;
2. кликнуть по строке таблицы.

Клик по иконке удаления не открывает форму редактирования.

## 3. Создание категории

Кнопка **«Создать категорию»** открывает модальное окно.

Форма содержит:

| Поле | Обязательное | Поведение |
|---|---:|---|
| Название категории | Да | Текстовое поле, до 255 символов |
| Цвет категории | Да | Цветовой контрол и рядом короткое hex-значение |

В той же строке, где находится выбор цвета, показывается preview категории в виде двунаправленной стрелки. Пользователь сразу видит, как категория будет выглядеть в таблице гостей.

## 4. Редактирование категории

Редактирование открывается из строки или по иконке карандаша.

Можно изменить:

- название;
- цвет.

Кнопка сохранения блокируется, если пользователь открыл форму и ничего не изменил.

Название категории должно быть уникальным внутри одного мероприятия. В разных мероприятиях одинаковые названия допустимы.

## 5. Удаление категории

Удаление открывает модальное подтверждение.

При удалении:

- категория удаляется;
- связи категории с гостями удаляются каскадно;
- сами гости остаются.

То есть удаление категории означает “снять эту категорию со всех гостей”, а не удалить гостей.

## 6. Использование в гостях

У гостя может быть только одна категория.

В форме создания/редактирования гостя поле **«Категория»** работает как single-select:

- сверху показывается выбранная категория в виде двунаправленной стрелки;
- ниже находится список доступных категорий;
- выбор новой категории заменяет предыдущую;
- можно выбрать вариант **«Без категории»**.

В таблице гостей категория отображается отдельной колонкой.

# Часть 2. Для разработчика

## 1. Модель данных

Категории представлены двумя сущностями:

```text
Category
GuestCategory
```

### `corebackend.categories`

Таблица хранит справочник категорий мероприятия:

- `id`;
- `event_id`;
- `name`;
- `color`;
- `created_at`.

Ограничения:

- PK по `id`;
- FK `event_id -> events.id` с каскадным удалением;
- уникальный индекс `(event_id, name)`.

### `corebackend.guest_categories`

Таблица связи гостя и категории:

- `guest_id`;
- `category_id`.

Ограничения:

- PK по `guest_id`;
- FK `guest_id -> guests.id` с каскадным удалением;
- FK `category_id -> categories.id` с каскадным удалением;
- индекс по `category_id`.

PK по `guest_id` является главным инвариантом: один гость не может иметь больше одной категории.

## 2. Backend: файлы и ответственность

| Файл | Ответственность |
|---|---|
| `Application/Entities/Category.cs` | Сущность категории |
| `Application/Entities/GuestCategory.cs` | Связь гостя и категории |
| `Application/Repositories/ICategoryRepository.cs` | Контракт чтения и CRUD категорий |
| `Application/Services/ICategoryService.cs` | Контракт бизнес-операций категорий |
| `Infrastructure/Data/Configurations/CategoryConfiguration.cs` | Таблица `categories`, FK и уникальность имени |
| `Infrastructure/Data/Configurations/GuestCategoryConfiguration.cs` | Таблица `guest_categories` и инвариант “одна категория на гостя” |
| `Infrastructure/Repositories/CategoryRepository.cs` | EF-доступ к категориям |
| `Infrastructure/Services/CategoryService.cs` | Permissions, нормализация имени/цвета, блокировка завершённого мероприятия |
| `Api/Contracts/CategoryContracts.cs` | DTO и request-контракты |
| `Api/Controllers/CategoriesController.cs` | HTTP API категорий |
| `Infrastructure/DependencyInjection.cs` | Регистрация repository/service |

`GuestService` дополнительно использует `ICategoryRepository`, чтобы проверять принадлежность выбранной категории тому же мероприятию, что и гость.

## 3. API

Все маршруты расположены под:

```text
/api/events/{eventId}/categories
```

| Endpoint | Назначение | Авторизация | Ответ |
|---|---|---|---|
| `GET /events/{eventId}/categories` | Получить категории мероприятия | `[Authorize]` + пользователь должен быть участником мероприятия | `CategoryDto[]` |
| `POST /events/{eventId}/categories` | Создать категорию | `CanCreateEvent` | `201 CategoryDto` |
| `PUT /events/{eventId}/categories/{categoryId}` | Изменить категорию | `CanCreateEvent` | `200 CategoryDto` |
| `DELETE /events/{eventId}/categories/{categoryId}` | Удалить категорию | `CanCreateEvent` | `204` |

`GET` не открыт анонимно. Он доступен авторизованному пользователю, который связан с выбранным мероприятием.

`POST`, `PUT` и `DELETE` дополнительно проверяют:

- мероприятие активно;
- у пользователя есть `create_event` в этом мероприятии;
- категория принадлежит этому мероприятию.

## 4. DTO

`CategoryDto`:

```text
id, eventId, name, color, createdAt
```

`CreateCategoryRequest` и `UpdateCategoryRequest`:

```text
name, color
```

`GuestDto` содержит категорию гостя отдельными nullable-полями:

```text
categoryId, categoryName, categoryColor
```

`CreateGuestRequest` и `UpdateGuestRequest` принимают:

```text
categoryId
```

Если `categoryId == null`, гость сохраняется без категории.

## 6. Frontend: состояние

`CategoriesPage` хранит:

- `categories`;
- `loading`, `saving`, `error`;
- `isModalOpen`;
- `editingCategory`;
- `deleteCategory`;
- `formData`.

После создания категория добавляется в локальный список и сортируется по названию. После редактирования заменяется только изменённая строка. После удаления строка удаляется из локального списка.

## 7. Валидация

Frontend использует обязательные поля формы и `input type="color"`.

Backend повторно проверяет:

- имя не пустое;
- длина имени не больше 255;
- цвет соответствует формату `#RRGGBB`;
- имя уникально внутри мероприятия;
- выбранная категория гостя принадлежит мероприятию гостя.

## 8. Миграции

Категории добавлены миграцией:

```text
20260909164934_AddEventCategories
```

Она создаёт таблицы `categories` и `guest_categories`, а также индексы для уникальности имени и поиска связей по категории.

## 9. Текущие особенности и ограничения

1. Цвет хранится строкой, без отдельного enum или палитры.
2. Контраст текста поверх выбранного цвета не рассчитывается динамически: текст всегда белый.
3. Удаление категории снимает её со всех гостей.
4. История изменения категории не хранится.
5. Список категорий на вкладке гостей загружается как справочник для фильтра и формы.
