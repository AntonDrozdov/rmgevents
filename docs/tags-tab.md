# Вкладка «Метки»: пользовательская логика и архитектура

Документ описывает функциональность меток внутри мероприятия. Метки похожи на категории: у них есть название и цвет, ими можно помечать гостей и фильтровать список гостей. Главное отличие: у одного гостя может быть несколько меток.

Документ состоит из двух частей:

1. правила и сценарии для пользователя системы;
2. техническое описание для разработчика.

Термины:

- **метка** — цветная бирка, которую можно назначить гостю;
- **бирка** — визуальное отображение метки: прямоугольный блок с точкой;
- **набор меток гостя** — список меток, связанных с гостем через many-to-many таблицу.

---

# Часть 1. Для пользователя системы

## 1. Когда доступна вкладка

Вкладка **«Метки»** находится внутри выбранного мероприятия:

```text
/events/{eventId}/tags
```

Она отображается пользователям с разрешением `create_event`.

Для стандартных ролей:

| Роль | Доступ к вкладке |
|---|---|
| `Administrator` | Да |
| `Manager` | Нет по умолчанию |
| `Creator` | Нет по умолчанию |
| Пользовательская роль | Да, если роли назначено `create_event` |

Если мероприятие завершено, метки доступны только для просмотра. Создание, редактирование и удаление скрыты на frontend и запрещены на backend.

## 2. Список меток

Вкладка показывает плоский список меток текущего мероприятия.

В таблице отображаются:

- название;
- цвет;
- дата создания;
- действия редактирования и удаления.

Метка отображается как бирка с точкой. Это визуально отделяет её от:

- статусов, которые остаются облаками;
- категорий, которые отображаются широкими двунаправленными стрелками.

Редактирование можно открыть:

1. кликом по строке;
2. кликом по иконке карандаша.

## 3. Создание метки

Кнопка **«Создать метку»** открывает модальное окно.

Форма содержит:

| Поле | Обязательное | Поведение |
|---|---:|---|
| Название метки | Да | Текстовое поле, до 255 символов |
| Цвет метки | Да | Цветовой контрол, hex-значение и preview бирки |

Preview находится в той же строке, что и выбор цвета, поэтому пользователь сразу видит внешний вид будущей метки.

## 4. Редактирование метки

Редактирование открывается из строки или по иконке карандаша.

Можно изменить:

- название;
- цвет.

Кнопка сохранения блокируется, если изменений нет.

Название метки должно быть уникальным внутри мероприятия. В разных мероприятиях одинаковые названия допустимы.

## 5. Удаление метки

Удаление открывает модальное подтверждение.

При удалении:

- метка удаляется;
- связи метки с гостями удаляются каскадно;
- гости остаются.

## 6. Использование в гостях

В форме создания/редактирования гостя можно выбрать несколько меток.

Поведение:

- выбранные метки показываются отдельной строкой;
- ниже расположен список всех доступных меток;
- клик по метке добавляет её гостю;
- повторный клик по выбранной метке снимает её;
- порядок хранения не является бизнес-значимым.

В таблице гостей метки отображаются отдельной колонкой **«Метки»** как набор бирок.

## 7. Фильтр по меткам

На вкладке гостей есть фильтр по меткам.

Можно выбрать несколько меток. Фильтр работает по принципу:

```text
гость должен иметь все выбранные метки
```

Например, если выбраны метки `VIP` и `Спикер`, в списке останутся только гости, у которых есть обе метки одновременно.

Кнопка **«Сбросить»** очищает выбранные метки фильтра.

# Часть 2. Для разработчика

## 1. Модель данных

Метки представлены двумя сущностями:

```text
Tag
GuestTag
```

### `corebackend.tags`

Таблица хранит справочник меток мероприятия:

- `id`;
- `event_id`;
- `name`;
- `color`;
- `created_at`.

Ограничения:

- PK по `id`;
- FK `event_id -> events.id` с каскадным удалением;
- уникальный индекс `(event_id, name)`.

### `corebackend.guest_tags`

Таблица связи гостей и меток:

- `guest_id`;
- `tag_id`.

Ограничения:

- составной PK `(guest_id, tag_id)`;
- FK `guest_id -> guests.id` с каскадным удалением;
- FK `tag_id -> tags.id` с каскадным удалением;
- индекс по `tag_id`.

Составной PK не позволяет привязать одну и ту же метку к одному гостю дважды.

## 2. Backend: файлы и ответственность

| Файл | Ответственность |
|---|---|
| `Application/Entities/Tag.cs` | Сущность метки |
| `Application/Entities/GuestTag.cs` | Связь гостя и метки |
| `Application/Repositories/ITagRepository.cs` | Контракт чтения и CRUD меток |
| `Application/Services/ITagService.cs` | Контракт бизнес-операций меток |
| `Infrastructure/Data/Configurations/TagConfiguration.cs` | Таблица `tags`, FK и уникальность имени |
| `Infrastructure/Data/Configurations/GuestTagConfiguration.cs` | Таблица `guest_tags` и many-to-many связь |
| `Infrastructure/Repositories/TagRepository.cs` | EF-доступ к меткам |
| `Infrastructure/Services/TagService.cs` | Permissions, нормализация имени/цвета, блокировка завершённого мероприятия |
| `Api/Contracts/TagContracts.cs` | DTO и request-контракты |
| `Api/Controllers/TagsController.cs` | HTTP API меток |
| `Infrastructure/DependencyInjection.cs` | Регистрация repository/service |

`GuestService` использует `ITagRepository`, чтобы проверять принадлежность всех выбранных меток мероприятию гостя.

`GuestRepository` отвечает за:

- загрузку `GuestTags.Tag` для `GuestDto`;
- полную замену набора меток гостя через `SetGuestTagsAsync`;
- фильтрацию гостей по набору выбранных меток.

## 3. API

Все маршруты расположены под:

```text
/api/events/{eventId}/tags
```

| Endpoint | Назначение | Авторизация | Ответ |
|---|---|---|---|
| `GET /events/{eventId}/tags` | Получить метки мероприятия | `[Authorize]` + пользователь должен быть участником мероприятия | `TagDto[]` |
| `POST /events/{eventId}/tags` | Создать метку | `CanCreateEvent` | `201 TagDto` |
| `PUT /events/{eventId}/tags/{tagId}` | Изменить метку | `CanCreateEvent` | `200 TagDto` |
| `DELETE /events/{eventId}/tags/{tagId}` | Удалить метку | `CanCreateEvent` | `204` |

`GET` не анонимный: он доступен только авторизованному пользователю выбранного мероприятия.

## 4. DTO

`TagDto`:

```text
id, eventId, name, color, createdAt
```

`GuestTagDto`:

```text
id, name, color
```

`CreateTagRequest` и `UpdateTagRequest`:

```text
name, color
```

`GuestDto` содержит:

```text
tags[]
```

`CreateGuestRequest` и `UpdateGuestRequest` принимают:

```text
tagIds[]
```

При редактировании гостя массив `tagIds` трактуется как полная новая версия набора меток. Если передан пустой массив или `null`, у гостя не остаётся меток.

## 5. Фильтрация гостей по меткам

`GET /events/{eventId}/guests` принимает query-параметр:

```text
tagIds
```

Frontend отправляет повторяющиеся query-параметры:

```text
?tagIds=1&tagIds=2
```

Backend применяет фильтр “содержит все выбранные метки”:

```csharp
foreach (var tagId in tagIds)
{
    query = query.Where(guest => guest.GuestTags.Any(guestTag => guestTag.TagId == tagId));
}
```

Такой вариант выбран как более точный: каждый следующий выбранный фильтр сужает список.

## 7. Frontend: состояние

`TagsPage` хранит:

- `tags`;
- `loading`, `saving`, `error`;
- `isModalOpen`;
- `editingTag`;
- `deleteTag`;
- `formData`.

`GuestsPage` дополнительно хранит:

- `tags` — справочник меток мероприятия;
- `formData.tagIds` — выбранные метки гостя в форме;
- `guestTagFilters` — выбранные метки фильтра таблицы.

## 8. Миграции

Метки добавлены миграцией:

```text
20260909181319_AddEventTags
```

Она создаёт таблицы `tags` и `guest_tags`, уникальный индекс `(event_id, name)` и индекс по `guest_tags.tag_id`.

## 9. Текущие особенности и ограничения

1. Цвет хранится строкой в hex-формате.
2. Контраст текста поверх цвета не рассчитывается динамически: текст всегда белый.
3. История изменения метки и история привязки меток к гостю не хранится.
4. Фильтр по нескольким меткам работает как AND, а не OR.
5. При удалении метки гости не удаляются, только очищаются связи.
